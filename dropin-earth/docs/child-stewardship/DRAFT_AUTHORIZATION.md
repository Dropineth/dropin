# Fresh authorization for each synthetic draft

Every new synthetic observation requires a fresh online per-draft capability, including generation-zero sessions. A recovered draft, a still-valid session token, previous consent, or a durable queue entry does not itself authorize sending the draft. The application obtains the capability only after the current principal explicitly authorizes the particular draft; a later send presents it in the same transaction as the observation.

`issue_draft_authorization(raw_bearer, proposal)` accepts only draft ID, intent digest, assignment ID, original session/consent epoch, purpose, schema version, policy version and current expected version. It receives no answer, sample ID, claimed capture time or full command. It hashes the raw bearer internally, locks the session and checks current generation, actor/device/epoch, scope, assignment, guardian link, learning/upload consent, assent, policy, age and task validity. The result is a random `cp-upload` capability, expiring within five minutes or the session deadline. SQL stores only its hash. Invalid issuance returns null.

`consume_draft_authorization(proof, session, actor, command)` accepts the actual closed synthetic command only at send time. It recomputes canonical SHA-256, verifies the intent digest, exact draft-derived command ID, assignment and version, and rechecks current authority under the session lock. The consumed record is immutable and stores command/proof hashes, command ID, expected version and minimal transaction bindings; it does not retain answer/sample/capture payloads. Invalid consumption returns false.

A database trigger requires a same-transaction consumption for every new observation and reconstructs its command digest from the actual proposed observation. The observation must retain synthetic source and E0 classification. Deferred validation rejects a consumed proof without the corresponding observation, rolling back both. Subsequent review can update the review state but cannot rewrite the admitted answer, source or capture claim. Exact request receipts also require a current valid proof. Repeating the same proof may return only the matching durable receipt; a newly issued proof can acknowledge that exact historical command while binding current authority. A receipt outcome retains only hashes and minimal replay facts, and does not rewrite the observation.

`tests/integration/child-stewardship-draft-authority.integration.ts` uses an actual restricted ephemeral LOGIN in a disposable local PostgreSQL database. Eleven tests including the parent test cover metadata-only issuance, canonical digest matching, generation-zero enforcement, valid review upserts, immutable content, forged direct inserts/updates/deletes, known-hash impersonation, altered commands/tenants/versions, rollback, generation changes, renewed consent epochs, exact receipt replay, deny-only rollback and expiry during a row-lock wait. The engineering lead's separate Hono suite verifies the application boundary and receipt retries.

Apply `child-stewardship-draft-authorization.sql` after base, authority and resume migrations. No production migration or role provisioning occurred. The rollback replaces issuance and consumption with deny-only functions, including for explicitly granted runtime roles, while preserving grants, replay records and the authorization trigger. The unmounted fixed-media fixture service remains a separate test capability; do not mount it for restored-session ingress without equivalent fresh per-object authorization. This protocol authorizes only fixed synthetic learning commands, not real uploads, identity verification, funds or environmental claims.
