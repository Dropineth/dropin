# Synthetic restore checkpoint verification

This optional module keeps a restored child-stewardship session unavailable until a dedicated verifier validates a current, independently signed checkpoint against the actual restored canonical state. It is not enabled in production. Local tests use ephemeral Ed25519 keys, restricted PostgreSQL login identities, and a temporary atomic JSON file outside the database backup. They do not demonstrate institutional checkpoint operation or production disaster recovery acceptance.

`child-stewardship-restore.sql` installs quarantine and immutable admission facts. `ChildRestoreVerifier` verifies exact canonical checkpoint bytes, two distinct current keys and control domains with protection and trustee roles, explicit key-registry version, current expiry, tenant, environment, and the independently current checkpoint digest. It checks the actual canonical, security and privacy roots before admission. Its connection must be a separately approved nonowner verifier login without other operational roles or memberships. SQL records the verifier's admission; SQL does not itself perform Ed25519 verification.

The roots include normalized E/C/R/F state, append-only economic and financial facts, pending obligations, nonce and epoch floors, registry/admission/replay state, media quarantine and review facts, agent registry and nonce facts, and deletion suppression, inventories, receipts and legal holds. Installed global role registries and the fixed media fixture manifest are covered too. Restore admission facts are excluded to avoid a self-referential digest. Ephemeral rate counters are not canonical financial or privacy authority. The separate, unlinked WebAuthn sandbox's data is not represented as a child session; its verifier role configuration is included.

The runtime requires a fresh external anchor provider on every guarded access when this module is installed. A configured requirement also fails closed when a restored older schema lacks the module. A copied admission or database OID alone is insufficient. The API store, operation verifier, media service, agent gateway and privacy worker use the shared current-anchor gate. Quarantine blocks privacy deletion as well as export: a stale backup may lack a later legal hold, so a queued old deletion is not current deletion authority. Separate cleanup helpers require the same current checkpoint and admission but permit an approved privacy worker to finish retention after the interactive session expires. They do not permit interactive access, export creation, new media, or arbitrary record writes. The worker still enforces exact deletion plans and current legal holds.

Recovery must keep ordinary database clients quiesced and their restored access absent while restoring. The native workflow restores without ACLs, grants only the dedicated verifier, commits quarantine, and then restores runtime privileges while the session remains closed. Only fresh exact-current admission opens access. An external application anchor cannot prevent arbitrary direct SQL access during an uncontrolled in-place rollback that retains active runtime permissions. The module does not claim to detect arbitrary DBA rollback or to reconstruct missing obligations from hashes. Stale canonical data must be recovered from a current authentic backup or journal; it is never synthesized or discarded to make a checkpoint pass.

The independently current checkpoint source and signing registry must survive the database restore and advance after relevant executions, revocations and deletion/retention changes. A cached or unavailable source is not acceptable. No such production authority, provider, role grant or credential has been created here. The rollback SQL closes execution while retaining checkpoint and audit history; deployment must keep clients stopped until a newly reviewed forward recovery and current checkpoint are admitted.

Native evidence is in `tests/integration/child-stewardship-restore.integration.ts`. It runs actual `pg_dump`/`pg_restore` into unique disposable local databases, including restoring a previously admitted backup into the same database OID while the external checkpoint remains newer. Test results are recorded outside the repository in the build evidence directory; final counts must come from the completed run. The test also covers narrow child-initiated privacy pause authorization, a single-connection verifier pool, expiry during an external-provider wait, and committed rollback with explicit worker grants.
