# Synthetic rights accounting and correction evidence

This slice executes synthetic XTS accounting only. There is no actual funding institution, provider dispatch, legal adjudication or currency exchange. Nonzero fees remain unsupported under the zero-fee policy. Dividing the amount of one entitlement into newly issued entitlements is unsupported; the legal-correction tests partition and merge sets of existing immutable entitlement IDs.

The native suite uses actual restricted PostgreSQL LOGIN identities, a separately scoped Ed25519 verifier, exact transition admission and normalized database persistence. One additional scenario uses the actual Hono rights route and `PostgresChildStore` for the complete 100/40/20/10 flow. Other direct database scenarios are not described as HTTP end-to-end tests.

A discovered source-replay defect was corrected: a provider operation cannot bind to two payouts, and one provider receipt cannot settle or refund more than one payout. Status progression for the same provider operation still accepts distinct valid receipts. Refund receipt IDs enter the same global source-receipt namespace within the synthetic tenant ledger. The kernel records policy-independent economic keys; PostgreSQL enforces their unique primary key, a unique provider-operation index, append-only receipt history and cross-payment receipt checks under the session lock. Concurrent settlement-source reuse permits one financial effect. Historical receipt callbacks and fresh HTTP idempotency retries do not produce new financial effects.

Database role and registry-publisher scope are checked after acquiring the session lock. The native expiry test uses an actual restricted LOGIN, confirms the statement waits behind a lock, waits across real scope expiry, and verifies rollback rather than retaining pre-wait permission.

The final receipt and scoped TypeScript/ESLint output are kept outside the repository in the task audit-report build directory. Earlier overwritten test receipts are explicitly disclosed in `child-rights-accounting-failure-history.md`; only observed excerpts are recorded there. The preserved full HTTP status-expectation failure is separate from the later passing receipt. Final release testing, fixed-SHA review and production acceptance remain separate gates.
