# Synthetic WebAuthn verification boundary

This module performs actual WebAuthn registration and authentication verification with pinned `@simplewebauthn/server` 14.0.3. It is an isolated local integration surface for synthetic authenticator fixtures. It is not mounted by the production application, does not enroll browser credentials, and alone does not issue a CanopyProof product session. The separately reviewed [guardian session bridge](GUARDIAN-SESSIONS.md) consumes recent authentication only for an explicitly provisioned synthetic guardian binding. Successful verification proves possession of the fixture key; it does not establish age, identity, guardianship, consent, or independent institutional authority.

The fixed relying party is `webauthn.synthetic.invalid`, with exact origin `https://webauthn.synthetic.invalid`. The trusted test harness supplies a credential ID and SHA-256 digest of its COSE public key before creating a sandbox. Neither pin is accepted from HTTP. Registration accepts only that key and ID, ES256, and `none` attestation. The fixture generates ephemeral keys in memory; private keys are not serialized or committed. No real name, email, media, coordinates, or biometric input is part of the ceremony API.

## Implementation

| Surface | Files and behavior |
| --- | --- |
| Verification service | [webauthn.ts](../../services/api/src/domain/child-stewardship/webauthn.ts): library verification of exact challenge, origin, RP ID, user presence, user verification, signature, current credential, and counter. |
| Durable state | [child-stewardship-webauthn.sql](../../services/api/prisma/child-stewardship-webauthn.sql): separate schema for fixture bindings, ceremonies, credentials, sessions, and append-only audit. Distinct non-owner runtime and admitted verifier roles, sandbox RLS, immutable binding, monotonic counters and revocation, and one-way challenge consumption. |
| Isolated HTTP adapter | [webauthn-fixture.ts](../../services/api/src/routes/child-stewardship/webauthn-fixture.ts): server-injected fixture scope, capability authentication, exact origin, closed JSON fields, 32 KiB body limit, and `no-store`. Deliberately not imported or mounted by the production application. |
| Authenticator fixture | [child-stewardship-webauthn.ts](../../tests/fixtures/child-stewardship-webauthn.ts): real Node P-256 key generation and ES256 signatures over authenticator data and the client-data hash. CBOR encoding is limited to test fixture construction; production verification uses the pinned library. |
| Native integration tests | [child-stewardship-webauthn.integration.ts](../../tests/integration/child-stewardship-webauthn.integration.ts): actual Hono requests and native PostgreSQL with distinct temporary non-owner, non-bypass runtime and verifier login identities. Ephemeral credentials exist only in memory and the disposable local database, and roles are removed at test teardown. |
| Rollback | [child-stewardship-webauthn.rollback.sql](../../services/api/prisma/child-stewardship-webauthn.rollback.sql): revoke fixture sessions, credentials, and sandboxes while preserving counters, consumed challenges, and audit records. No production deployment has occurred. |

Challenges expire after two minutes and are consumed on a verification attempt, including a rejected signature. A database failure rolls back challenge consumption, counter advancement, session creation, and audit together, allowing a safe retry. Registration creates no session. Authentication issues a random token stored only as a hash, valid for at most ten minutes and no longer than the sandbox lifetime. Every session lookup checks current credential revocation and account/credential epochs. Sandbox revocation invalidates existing sessions and queued challenges and cannot be reversed by this API.

Authenticators that report counter zero are supported as specified by the verifier. Single-use challenges remain mandatory; a zero counter is not treated as clone detection. A nonzero counter cannot move backward. A fixture sandbox is an hour-long test scope, not account recovery or a reusable real identity record.

Verification uses a separate SQL client and database role. Only an enabled, unexpired role provisioned by the migration owner may insert credentials or sessions, advance counters, or append accepted authentication/registration audit entries. Ordinary runtime SQL attempts are denied by triggers even when table DML privileges are granted. The ordinary runtime cannot enroll itself into the verifier registry. Readiness rejects shared roles, owner/bypass roles, switched login identities, and runtime membership in the verifier role. Native tests connect as the actual restricted login identities: resetting role does not elevate authority, and switching to the verifier role is denied. The verifier transaction still runs the actual library checks before writing; a caller-supplied `verified` flag or session GUC grants no admission. These controls were added after independent review identified that the initial single-runtime-role design allowed direct SQL session insertion.

## Executed validation

Using the pinned Node 22.22.3 / npm 10.9.4 environment and the explicitly disposable native PostgreSQL test database:

```sh
node --import tsx --test --test-reporter=tap tests/integration/child-stewardship-webauthn.integration.ts
./node_modules/.bin/tsc --noEmit --strict --skipLibCheck --noUncheckedIndexedAccess --exactOptionalPropertyTypes --target ES2022 --module NodeNext --moduleResolution NodeNext services/api/src/domain/child-stewardship/webauthn.ts services/api/src/routes/child-stewardship/webauthn-fixture.ts
./node_modules/.bin/eslint services/api/src/domain/child-stewardship/webauthn.ts services/api/src/routes/child-stewardship/webauthn-fixture.ts tests/fixtures/child-stewardship-webauthn.ts tests/integration/child-stewardship-webauthn.integration.ts
```

All 14 reported tests passed (13 subtests plus the parent test); focused strict type checking and lint passed. Coverage includes genuine registration/authentication and reconnect, challenge replay and expiry, invalid origin/RP/UV/UP/cross-origin data, unsupported COSE algorithm, the same credential ID paired with a different key, invalid signatures, foreign user handles, counter rollback and counter-zero operation, concurrent redemption, current revocation, transaction failure rollback, tenant isolation, rejected caller-supplied verification flags, sanitized audit, and non-destructive rollback. Native adversarial SQL also attempts to mint a known-token session, insert a credential, advance a counter, forge accepted audit, and self-provision verifier admission from the ordinary runtime; all are denied. Disabling verifier admission blocks a valid cryptographic response without consuming its challenge or changing the counter/session, and an approved retry succeeds after admission is restored. A native row-lock wait across ceremony and sandbox expiry is rejected: the trusted server instant advances by monotonic elapsed time across waits and crypto work, with deadline checks after locks, verification, and persistence. The test intercepts external fetch and asserts zero calls. Local evidence is retained outside the repository at `/workspace/canopyproof-audit-report/build/child-webauthn-native.tap`.

## Requirements and remaining gates

This supplies a tested cryptographic and durable-state implementation slice for the identity/passkey requirements and replay/revocation portions of the security acceptance matrix. It does not close ID requirements or production acceptance by itself. The ceremony HTTP integration remains the isolated fixture router. The separate guardian bridge now reaches the existing child session boundary for prebound synthetic accounts; that does not authorize production enrollment. The dedicated verifier and migration credentials remain trusted authority; these tests deny ordinary runtime SQL forgery but do not claim resistance to compromise of the verifier process or its database credential. Deployment must preserve role separation, avoid runtime membership or credential access to the verifier role, and provision reviewed, expiring admission through a migration authority. No production role grants were performed.

Real enrollment remains disabled until jurisdiction, safeguarding, guardian evidence, independent review, and applicable G2/G4 gates are satisfied. Browser/platform authenticator interoperability, real account linking, recovery, production RP/origin configuration, real-account product session integration, deployment-role provisioning, backup/retention operations, and human acceptance are unrun or unimplemented here. No FIDO certification or real-world provider acceptance is claimed. Production activation requires a separately reviewed design and release; changing the fixed RP constant is insufficient.

The implementation follows the official [SimpleWebAuthn server API documentation](https://simplewebauthn.dev/docs/packages/server) and the pinned [14.0.3 release](https://github.com/MasterKale/SimpleWebAuthn/releases/tag/v14.0.3).
